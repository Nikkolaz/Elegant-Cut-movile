1. DIAGNÓSTICO DE LA ESTRUCTURA ACTUAL
---------------------------------------

lib/
├── main.dart
└── src/
    ├── api/           -> Servicios de API organizados por entidad
    ├── pages/         -> Pantallas de la app (sin agrupar por feature)
    ├── theme/         -> Tema global de la app
    ├── utils/         -> Constantes y utilerías
    └── widgets/       -> Widgets reutilizables y tabs

VALORACIÓN: 5/10 - Estructura básica funcional pero con carencias
importantes para escalar.


2. PROBLEMAS DETECTADOS
------------------------

 a) Sin gestión de estado:
    No hay BLoC, Riverpod, Provider ni nada similar.
    Usar setState() con llamadas API, autenticación y múltiples
    pantallas se vuelve insostenible al crecer.

 b) Sin modelos (models/):
    Los datos (Barber, Booking, Service, User, etc.) se manejan
    probablemente como Map<String, dynamic>. Sin modelos tipados
    con fromJson/toJson, no hay seguridad de tipos ni autocompletado.

 c) Sin repositorios (repositories/):
    Las páginas llaman a la API directamente. Un Repository
    actúa como intermediario entre la capa de datos (API local/remota)
    y la lógica de negocio, facilitando testing y cambios de fuente.

 d) Widgets mal categorizados:
    - cuts_history_tab.dart, favorite_barbers_tab.dart,
      notifications_tab.dart NO son widgets genéricos; son
      secciones completas que deberían estar agrupadas por feature.
    - Mezcla widgets reutilizables (service_card, custom_toast)
      con "tabs" específicas de funcionalidad.

 e) Sin sistema de rutas centralizado:
    - No hay un router dedicado (GoRouter, auto_route, o
      siquiera un app_router.dart).
    - La navegación está dispersa en los Navigator.push
      directos desde cada página.

 f) Páginas planas y desordenadas:
    - 16 archivos sueltos en pages/ sin agrupar por funcionalidad.
    - admin/ tiene su subcarpeta pero el resto no sigue ese patrón.

4. EXPLICACIÓN DE CADA CARPETA
--------------------------------

main.dart
  - Punto de entrada de la app.
  - Solo debe llamar a runApp(App()).

app.dart
  - Widget raíz StatelessWidget.
  - Configura MaterialApp.router (tema, rutas, localizaciones).

core/
  - TODO lo transversal que se usa en múltiples capas.
  - No depende de ninguna feature.
  - constants/    : Valores fijos (colores, strings, dimensiones).
  - theme/        : Definición de ThemeData (light/dark).
  - network/      : Cliente HTTP, interceptors, endpoints.
  - utils/        : Funciones helper y validators genéricos.

data/
  - Capa de datos pura. SIN dependencia de Flutter.
  - models/       : Clases Dart con fromJson/toJson.
                    Representan las entidades del negocio.
  - repositories/ : Abstracción entre la fuente de datos
                    (API, local DB) y la capa de estado.
                    Cada repositorio usa uno o más servicios API.

state/
  - Gestión de estado (BLoC, Riverpod, Provider, etc.).
  - Separa UI de lógica de negocio.
  - Idealmente 1 Bloc/Provider por feature.
  - Los eventos y estados se definen aquí.

router/
  - Define TODAS las rutas de la app en un solo lugar.
  - Usa GoRouter (recomendado) o auto_route.
  - Facilita navegación con parámetros, deep linking, guards.

features/
  - Corazón de la app. Cada feature es autocontenida.
  - Cada subcarpeta tiene su página principal y sus widgets
    específicos (NO compartidos con otras features).
  - Si una feature crece mucho, puede tener subcarpetas:
    pages/, widgets/, tabs/, etc.

shared/widgets/
  - Widgets que NO pertenecen a una feature específica y
    pueden reutilizarse en cualquier parte de la app.


5. BENEFICIOS DE ESTA ESTRUCTURA
---------------------------------

  + ESCALABILIDAD: Agregar una nueva feature no desordena
    el proyecto; solo creas una carpeta en features/.

  + SEPARACIÓN DE CONCEPTOS: Cada capa tiene una
    responsabilidad única y bien definida.

  + TESTEABILIDAD: Al separar data, state y UI, cada capa
    se prueba de forma independiente.

  + MANTENIBILIDAD: Sabes exactamente dónde buscar cada
    cosa sin adivinar.

  + COLABORACIÓN: Varios desarrolladores pueden trabajar
    en distintas features sin conflictos.

  + REUTILIZACIÓN: Los widgets compartidos están en
    shared/ y los específicos dentro de su feature.


6. ¿ES UNA BUENA ESTRUCTURA PARA FLUTTER?
------------------------------------------

SÍ, esta estructura sigue los principios recomendados
por la comunidad Flutter y arquitecturas limpias como
Clean Architecture adaptada a Flutter.

No es la única válida, pero es un estándar probado en
proyectos medianos y grandes. Para apps pequeñas puede
sentir "demasiada carpeta", pero a largo plazo siempre
gana en claridad y mantenibilidad.

Alternativas populares:
  - Feature-first (la que propongo aquí) -> Recomendada
  - Layer-first (todo models/ junto, todo pages/ junto)
    -> Similar a tu estructura actual, buena solo para
       apps muy pequeñas.
  - Clean Architecture (domain/data/presentation)
    -> Más académica, ideal para equipos grandes.

Para Elegant Cut, que tiene auth, booking, barbers,
admin, shop, PQRS y múltiples servicios, la estructura
feature-first es la mejor opción.
